# Qairon API Inventory & Multitenancy Gap Analysis

Scope: everything required to take Qairon from a single-operator, trusted-network deployment-management system to a **multitenant product** whose entire GUI is replaced by a React Flow (or similar) graph-first frontend.

---

## 1. Executive Summary

Qairon today is an **anonymous-by-design, single-tenant** system:

- The entire API surface (~35 resources × full CRUD) is auto-generated by Flask-Restless-NG from SQLAlchemy models and mounted **without any authentication, authorization, tenancy, quotas, or rate limiting**.
- There is **no user, tenant, organization, role, session, token, or audit concept anywhere** in the schema or server code.
- All primary keys are **globally-unique composite natural keys** (colon-delimited canonical IDs). Every tenant will want an environment named `prod` — the ID scheme itself is the single biggest multitenancy obstacle.
- The current GUI is thin Flask-Admin CRUD with zero business logic of its own; replacing it with React Flow loses nothing, but the API lacks the graph, real-time, and spec/typing endpoints a modern SPA needs.

The work therefore splits into four tracks:

| Track | Nature | Risk if skipped |
|---|---|---|
| A. Identity & tenancy data model | Greenfield design (nothing to retrofit) | Product cannot ship |
| B. API hardening & scoping | Retrofit one enforcement point (single API factory loop) | Cross-tenant data leaks |
| C. Graph/UX-serving API for React Flow | New endpoints | SPA is slow/unshippable (N+1 over JSON:API) |
| D. Observability stack isolation | Config + proxy work | Tenant metrics/logs visible to all |

## 2. Current Architecture Snapshot

```
qcli (CLI) ──HTTP──► Flask app ──SQLAlchemy──► PostgreSQL
Browser ───────────► Flask-Admin (server-rendered, Bootstrap4/slate)
                     Flask-Restless-NG:
                       /api/rest/v1/*  (page_size=0 → unbounded dumps)
                       /api/qcli/v1/*  (page_size=5, custom scalar serializer)
                     Hand-written: /up, /api/tf/v1/* (config gen), /api/rest/v1/deployment/<id>/json
Sidecar stack (docker-compose): VictoriaMetrics :8428, VictoriaLogs :9428,
                                Tempo :3200/:4317/:4318, Grafana :3000 (admin/admin)
```

Key wiring facts (verified in `app.py`, `base.py`):

- Two `APIManager` instances register **every model** in `models/` plus every plugin model (`plugins/dependencies/`) with `methods=['GET', 'POST', 'DELETE', 'PATCH']`, `allow_client_generated_ids=True`, `allow_to_many_replacement=True`.
- `/api/rest/v1` uses `page_size=0` — **every collection GET returns the entire table**.
- Flask-Talisman is enabled (CSP, HTTPS headers) — good baseline, but it is the *only* security middleware present.
- `flask-cors` is in `requirements.txt` but **never imported or initialized** — there is no CORS support today. A separately-hosted React SPA cannot call this API cross-origin until that changes.
- `SECRET_KEY` comes from the environment; with `app.debug` the Werkzeug debugger is mounted with `evalex=True` (interactive RCE console) — must be hard-disabled in any product build.
- Config rendering uses `ast.literal_eval` over `defaults`/`config` text blobs at request time (`/api/tf/v1/...`) — unvalidated tenant-supplied input into eval-adjacent parsing.

## 3. API Inventory

### 3.1 Auto-generated JSON:API resources (Flask-Restless-NG)

**36 resources** (32 core models + 4 dependencies-plugin models) are registered on **two** managers — `/api/rest/v1/{collection}` (unpaginated, standard JSON:API envelope) and `/api/qcli/v1/{collection}` (page 5/max 100, flattened scalar output via `QcliSerializer`) — for a total of **72 registrations**. Each registration exposes the full JSON:API route family:

```
GET|POST   /api/{rest|qcli}/v1/{collection}
GET|PATCH|DELETE /api/{rest|qcli}/v1/{collection}/{id}
GET        /api/{rest|qcli}/v1/{collection}/{id}/{relationship}          (related objects)
GET|POST|PATCH|DELETE /api/{rest|qcli}/v1/{collection}/{id}/relationships/{rel}  (linkage)
```

Plus `filter[objects]` query DSL (arbitrary field ops, `and`/`or` compounds), `page[size]`/`page[number]`, client-generated IDs, and full to-many replacement. **Effective endpoint count: several hundred routes, all anonymous, all writable.**

**`exclude` semantics (verified against Flask-Restless-NG 3.3.0 source):** the model `exclude` lists appear in exactly two places in the codebase — the `create_api()` calls in `app.py` and the Flask-Admin views (`form_excluded_columns`). What the `create_api` argument actually does is narrower than it looks:

- It takes effect **only on the `/api/rest/v1` registrations**: the library applies `exclude` solely when constructing its own default serializer (`manager.py:549-552`), where it removes those fields from the document body (`attributes` + `relationships` linkage).
- On the `/api/qcli/v1` registrations the argument is **dead code**: a custom `QcliSerializer` is passed, so `exclude` is silently discarded — and the serializer is constructed in `app.py:61` without an exclude list. All relationships are serialized (to-many collections get fully loaded per row — a hidden query cost), then the flattener drops all to-many linkage regardless of exclude and lifts to-one linkage into `<rel>_id` fields — including "excluded" ones.
- **No REST-reachable data is ever made unreachable by `exclude`.** Traversal routes (`GET /{collection}/{id}/{relation}`, `/relationships/{relation}`) resolve relations by raw model introspection with no exclude check, and `?include={relation}` loads excluded relations into the compound document's `included` array (though without linkage from the primary resource, standard JSON:API clients can't attach them).

Consequence: `exclude` is a payload-shaping knob for `/api/rest/v1` document bodies and Flask-Admin forms — **not** an access-control mechanism and not a consistent API contract across the two managers. Every relationship on every model is reachable anonymously.

**Dependencies plugin** (collections `dependency_case`, `dependency`, `relatable`, `related`; tables prefixed `plugin_dependencies_*`): a typed, directional dependency graph over arbitrary qairon entities. `DependencyCase` declares "type X may depend on type Y" with OTO/OTM cardinality; `Relatable` wraps a source entity, `Related` wraps target entities, both holding the entity's composite ID in `object_id` as a **plain string with no FK** (soft reference — renames/deletes silently orphan graph rows). Cardinality is stored but never enforced; validation is assert-based (API misuse → 500) and one validator silently nulls the relationship on type mismatch instead of raising. **This plugin is the natural backing store for React Flow edges — and currently its weakest link.**

**Audit/tenancy fields present today:** `created_at` and `last_updated_at` on every table. That is the complete list — no `created_by`, no owner, no tenant, no soft-delete.

### 3.3 CLI (qcli) surface — the API's primary consumer

qcli talks **exclusively to `/api/rest/v1`** (the unpaginated manager; `/api/qcli/v1` and its custom serializer are effectively unused by the shipped CLI). Server URL comes from `QAIRON_ENDPOINT` (default `http://127.0.0.1:5001`), **read once at import time into a class attribute**. Headers are JSON:API content-type only — **no auth header exists anywhere in the client**.

Generic verbs (registered for all 26 core resources + plugin resources): `list` (paginated GET following `links.next`), `query` (raw Flask-Restless `filter[objects]` JSON), `get`, `get_field` (related-collection GET), `set_field` (PATCH attribute), `create` (POST; server composes composite IDs from parent FK + name — **the CLI never builds IDs**), `delete`.

Resource-specific operations:

| Operation | Mechanism | Multitenancy hazard |
|---|---|---|
| `service assign_repo` / `unassign_repo`, `deployment assign_zone` / `unassign_zone` | GET current linkage → **full-replacement PATCH** of `/relationships/{rel}` | Under scoped visibility, read-modify-write **silently drops linkage rows the caller can't see** |
| `network allocate_subnet` | **Client-side** free-CIDR computation from `GET network/{id}/subnets`, then POST | Race-prone today; under tenant scoping, partial visibility ⇒ overlapping allocations. Must become a server-side transactional endpoint |
| `deployment clone` | GET → strip → POST + re-POST configs/procs/allocations | Stale (uses legacy resource names + a removed query signature) |
| aws plugin (`register_secret` etc.) | GET/POST `deployment_config` + boto3 Secrets Manager | Second credential domain (ambient AWS creds) |
| bake plugin (`files`) | ~6 GETs (build, deployment, configs, target, repos) + local file rendering | Read-heavy CI consumer; needs a machine token |
| dependencies plugin (`get_related`) | filtered GET on `related`, then per-row GET on the target entity | N+1 pattern |
| Tab completion | `filter[objects]` `like` queries on `id` | Enumerates the full ID namespace; fires duplicate requests; `assert status==200` crashes on 401 |

Pre-existing CLI breakage found while tracing (relevant because a product API must not inherit these silently): `get_field_query` verb has a parser but no implementation; `promote`/`setver`/`get_version` have dispatch entries but no parsers; `get_parent` passes a kwarg its callee doesn't accept; completer helper `_complex_list_` doesn't exist.

### 3.4 Current GUI (being replaced)

Flask-Admin mounted at `/admin`, Bootstrap4/slate theme, organized into 10 menu categories. Every view is a thin `ModelView` subclass differing only in search/filter columns and a custom CIDR form converter — **there is zero business logic in the GUI layer**. Replacing it with React Flow loses nothing; everything the GUI can do, the JSON:API endpoints already do. What the GUI provides that the API does not: CSV export buttons and human-friendly forms — both trivially reproduced client-side.

Part of the product story (deployment-aware monitoring), currently wide open and single-tenant:

## 4. Multitenancy Gap Analysis

Ordered by severity. **P0 = product cannot ship multitenant without it.**

### 4.1 Identity & authentication — P0, greenfield

Nothing exists: no User/Tenant/Org/Role/ApiKey models, no session or token verification, no `before_request` auth hook, no Flask-Restless preprocessors (the natural hook point — currently unused on all 72 registrations), and the Flask-Admin UI plus all hand-written routes are anonymous. `SECRET_KEY` is loaded but secures nothing meaningful.

Required:
- **Control-plane models**: `tenant`, `user`, `membership` (user↔tenant with role), `api_token` (hashed, scoped, expiring — for qcli and CI), optionally `service_account`.
- **Human auth**: OIDC (Authorization Code + PKCE) for the React SPA. Don't build password auth; delegate to an IdP and keep only the OIDC subject → user mapping.
- **Machine auth**: bearer tokens for qcli, the bake/aws plugins, and CI integrations (the GitHub Actions pattern in the README is a first-class use case).
- **Enforcement point**: one `before_request` middleware resolving `(tenant, principal, role)` + Flask-Restless `preprocessors` on every registration for query filtering. The single `create_api` loop in `app.py:60-78` is the one place to wire this — a genuine advantage of the generated-API design.

### 4.2 Tenancy & the ID scheme — P0, the central design decision

Every PK is a **globally-unique natural key**. `environment 'prod'`, `application 'social'`, `provider_type 'aws'` are singleton rows; composite IDs cascade textually into children (12-segment `release_id`). Two tenants cannot coexist in one namespace.

| Option | Mechanics | Pros | Cons |
|---|---|---|---|
| **A. Tenant prefix in the ID** | `{tenant}:prod:aws:…` | Minimal query changes; IDs stay globally unique | **Violates the project's own canonical-ID doctrine** (no prefixed variants); breaks every downstream consumer (qcli, fixtures, monitoring tags, Grafana queries, docs); tenant renames impossible |
| **B. `tenant_id` column + Postgres RLS** | Composite PK `(tenant_id, id)`; RLS policies; `SET app.tenant_id` per request | Industry standard; DB-enforced isolation; single schema to migrate | Every FK becomes composite; every string-concatenation ID listener, every association table, and the plugin's soft `object_id` references need rework — the **largest** migration of the three |
| **C. Schema-per-tenant** | Postgres schema per tenant; `search_path` set per request; shared `public` control-plane schema | **Zero model changes** — canonical IDs stay exactly as documented, per tenant; strong isolation; per-tenant export/delete/restore is `pg_dump` of one schema; honors the CLAUDE.md doctrine | Migrations fan out across N schemas (Alembic loop); connection pooling must be search_path-safe; awkward beyond ~low-thousands of tenants; cross-tenant analytics needs a separate path |
| **D. Database-per-tenant** | Full DB per tenant | Maximum isolation | Heavy ops burden; overkill for this stage |

**Recommendation: C (schema-per-tenant)** for the data plane with a shared control-plane schema for tenants/users/tokens. It is the only option that keeps the canonical composite-ID architecture — the system's core design commitment — completely intact, and it converts "tenant offboarding + data export" (a real enterprise requirement) into a one-liner. Option B is the fallback if the target market is high-volume self-serve with tens of thousands of small tenants.

Also required regardless of option: **reference-data policy**. `provider_type`, `deployment_target_type`, `language`, `repo_type`, `allocation_type` are arguably global catalog data; under C they're cheap to seed per schema (the fixture generator already does this), which also lets tenants customize them.

### 4.3 Authorization — P0

Beyond tenancy, the product needs intra-tenant roles. Minimum viable: `owner` / `editor` / `viewer` per tenant, enforced in the same preprocessor layer. The schema's own hierarchy invites finer scoping later (e.g. editor rights limited to an `environment` or `application` subtree — the composite ID prefix makes subtree checks a string-prefix match, a genuinely nice property of this design). Also: **DELETE and PATCH are currently enabled on all 36 resources including reference data** — method allow-lists should become role-dependent.

### 4.4 API hardening — P0/P1

| Gap | Detail | Priority |
|---|---|---|
| Unbounded reads | `/api/rest/v1` has `page_size=0` — any GET dumps the entire table (fixture scale: millions of rows). DoS-by-default | P0 |
| Client-generated IDs | Real on the 8 natural-key resources + `dependency_case`; must be validated/namespaced | P0 |
| To-many full replacement | `allow_to_many_replacement=True` + qcli's read-modify-write ⇒ cross-tenant linkage clobbering under scoped visibility | P0 |
| Werkzeug debugger | `evalex=True` when `app.debug` — interactive RCE console; must be impossible in product builds | P0 |
| `ast.literal_eval` on stored blobs | `defaults`/`config` parsed at request time in tf-gen paths | P1 (dead route today, but the pattern recurs) |
| No rate limiting / quotas | Nothing per-IP, per-token, or per-tenant | P1 |
| `exclude` typos inflate payloads | `DeploymentTarget` excludes nonexistent `deployment_targets` (so every `/api/rest/v1` response inline-serializes its full `deployments` linkage — unbounded fan-out at scale); `Fleet` excludes `deployment_targets` (attr is `deployment_target`). Not a confidentiality issue — hop endpoints ignore `exclude` anyway (§3.1) — but a real response-size problem under `page_size=0` | P1 |
| Dual API managers | `/api/rest/v1` vs `/api/qcli/v1` double the surface to secure and don't even share field-visibility behavior (the qcli manager silently discards `exclude` — §3.1); the qcli manager's serializer is unused by the actual CLI and has a stale-variable bug in the plugin loop | P1 — collapse to one |
| Assert-based validation | Plugin listeners raise `AssertionError` → 500 on bad input; validators silently null relationships | P1 |
| Dead endpoints | Both `/api/tf/v1` routes NameError at request time | P1 — delete or rebuild |

### 4.5 Data-integrity debt that tenancy inherits — P1

These are latent today; under multitenant load they become incidents:

- **No cascade behavior anywhere** — FKs are bare strings with no `ON UPDATE/ON DELETE`, no ORM `cascade=`. ID-recomputing listeners fire on update, so renaming a node strands its entire subtree with stale composite FKs.
- **No-op constraints**: `Allocation`'s UniqueConstraint/Index and `Dependency`'s UniqueConstraint are bare class-body expressions, never attached via `__table_args__` — they enforce nothing.
- **Association tables without PKs** — duplicate M2M rows possible; `deployment_current_release` allows multiple current releases per deployment.
- **Nullable columns used in PK concatenation** (`Provider.native_id`, `Fleet.name`, `Capacity.allocation_type_id`, `ServiceConfig`/`StackConfig` FKs) — TypeError on insert with legal-per-schema input.
- **Soft references in the dependencies plugin** — `object_id` strings with no FK; graph rows orphan silently.

### 4.6 qcli readiness — P1

The CLI is the paying customer's automation surface and currently assumes anonymous localhost:

- No auth header injection point: headers are frozen default-arg constants across ~9 call sites; no `requests.Session`. Needs a small refactor + `~/.qairon/config` (endpoint, token, tenant) + `QAIRON_TOKEN` env support.
- Endpoint URL evaluated at import time — per-invocation/per-profile selection impossible without re-import.
- Anonymous-success assumptions: completers `assert status==200` (401 crashes tab completion); catch-all `exit(255)` makes auth failures opaque.
- `allocate_subnet` must move server-side (transactional, tenant-scoped).

### 4.7 Observability tenancy — P1/P2

The monitoring pipeline is a headline feature, so tenant isolation here is product-critical: VictoriaLogs tenant headers (`AccountID`/`ProjectID`) on ingest + a query proxy; VictoriaMetrics needs the cluster version or vmauth label enforcement; Tempo `X-Scope-OrgID`; Grafana per-tenant orgs/folders or (better for "wow") **embed the graphs natively in the React app** by querying the datasources through your own authenticated proxy and rendering with your own charts — which also solves the hardcoded-datasource-UID portability problem.

### 4.8 Product operations — P2

No audit log (who changed what — `created_by`/`updated_by` columns plus an append-only event table), no tenant lifecycle (onboarding provisioning, offboarding export/purge), no usage metering for billing, no per-tenant backup/restore story (free under schema-per-tenant), no terms-of-service/data-residency handling.

## 5. Gaps for a React Flow Frontend

The data model is *already a graph* — two trees (infrastructure: environment→provider→region→partition→target; application: application→stack→service) joined by `deployment` edges, plus the dependencies plugin's typed entity graph. That's an unusually good fit for React Flow. What's missing is an API that serves it as a graph instead of 36 separate CRUD collections:

| Gap | Why it blocks the SPA | Proposed shape |
|---|---|---|
| **No topology endpoint** | Rendering one canvas today = dozens of collection GETs + client-side joins (N+1 over JSON:API). The CLI's `get_related` already shows the N+1 pattern | `GET /api/v2/graph?root={id}&depth=N&types=…` returning `{nodes:[{id, type, label, status, counts}], edges:[{source, target, kind}]}` in one query (recursive CTE; composite-ID prefix matching makes subtree queries cheap) |
| **No aggregation/rollup endpoints** | Node badges ("3 deployments, 1 degraded, current release :152") each cost a query | Per-node summary in the graph payload + `GET /api/v2/summary/{id}` |
| **No CORS** | flask-cors is in requirements but never initialized — a separately-hosted SPA can't call the API at all | Initialize CORS with an allow-list, or serve the SPA same-origin |
| **No OpenAPI spec** | Flask-Restless-NG emits no schema → no typed client, no codegen for the frontend team | Generate a spec for the v2 surface (or hand-write it — the resource census in §3.1 is the spec) |
| **No real-time channel** | Deployment status changes (the "wow" demo: watching a release roll across regions live on the canvas) require polling | SSE (simplest — works through proxies, one-directional fits the use case) publishing entity-change events; the `before_insert/update` listeners are a natural event source |
| **No layout persistence** | React Flow node positions/viewport are user state | New control-plane resource: `canvas_layout` (per user, per tenant, per view) |
| **No cross-type search** | A single search box over all entity types is table stakes for a graph UI | `GET /api/v2/search?q=` — the universal `id` string format makes a trigram index on `id` across tables very effective |
| **No optimistic concurrency** | Two users editing one canvas will clobber each other | `last_updated_at` already exists on every row — expose as ETag / `If-Unmodified-Since` |
| **No bulk mutations** | Drag-drop reparent or multi-node edit = many serial PATCHes; composite-ID recomputation makes rename-cascades multi-request | JSON:API `atomic:operations` extension or a purpose-built `POST /api/v2/mutations` batch endpoint |
| **Dependencies plugin integrity** | The edge store for the marquee visualization has no FK integrity, no cardinality enforcement, silent-null validators | Harden it (real FKs where possible, enforce `allowed_relationship`, replace asserts with 4xx) before building the UI on it |

`★ Insight ─────────────────────────────────────`
The composite-ID design that hurts multitenancy (global natural keys) is precisely what helps the graph UI: because every child ID textually contains its ancestor path, "give me the subtree under `prod:aws:111111111111`" is a single `LIKE 'prod:aws:111111111111:%'` — no recursive joins needed for hierarchy queries, only for the dependencies graph. The gap analysis and the React Flow plan pull the ID scheme in opposite directions, which is why the schema-per-tenant recommendation (keep IDs, isolate namespaces) resolves both.

## 6. Recommended Phasing

**Phase 0 — Debt & hardening (prerequisite, ~small):** delete dead `/api/tf/v1` routes and stale CLI paths; fix `exclude` typos; attach the no-op constraints via `__table_args__`; add PKs to association tables + a partial unique index for one-current-release; default pagination on all managers; collapse to a single API manager; kill the debug/evalex path; initialize CORS.

**Phase 1 — Control plane & tenancy (P0, ~large):** tenant/user/membership/api_token models in a shared schema; OIDC + PAT verification middleware; schema-per-tenant provisioning + Alembic multi-schema migration loop; Flask-Restless preprocessors for role checks; qcli auth support (Session + config file + token env var); server-side transactional `allocate_subnet`.

**Phase 2 — API v2 for the SPA (~medium-large, parallelizable with late Phase 1):** graph/topology endpoint, summary rollups, cross-type search, SSE event stream, canvas_layout resource, batch mutations, ETags, OpenAPI spec; harden the dependencies plugin.

**Phase 3 — React Flow frontend (~large):** canvas views (infra topology, service dependency graph, deployment/release flow), live deployment rollout animation from SSE, embedded metrics panels via authenticated datasource proxy; retire `/admin`.

**Phase 4 — Product ops (~medium):** audit log, quotas & rate limiting, usage metering, tenant lifecycle automation, observability-stack tenancy (VL tenant headers, vmauth/cluster VM, Tempo org IDs).

### Open decisions (owner: you)

1. **Isolation model** — schema-per-tenant (recommended, §4.2) vs RLS. Driven by expected tenant count and self-serve vs enterprise sales motion.
2. **Reference-data policy** — per-tenant catalogs (customizable) vs global shared catalogs (consistent). Schema-per-tenant defaults to per-tenant.
3. **API strategy for the SPA** — keep generated JSON:API + add a v2 graph layer on top (recommended: preserves qcli compatibility), vs replace wholesale with a hand-built API (cleaner, but breaks the CLI and forfeits the generated CRUD that is genuinely fine for 80% of operations).
4. **Grafana's role** — embed/proxy vs replace with native charts in the React app.
